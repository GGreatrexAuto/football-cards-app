# Football Cards Application - Test Plan

## 1. Introduction

This document outlines the comprehensive test plan for the Football Cards application, covering the initial three phases of development. The plan details the scope, approach, resources, and schedule of all testing activities. Its purpose is to ensure that the application meets the specified requirements and quality standards before release.

## 2. Test Strategy

Our test strategy is based on the test pyramid, emphasizing a strong foundation of unit tests, a focused set of integration and contract tests, and a lean layer of end-to-end UI tests. This approach enables early feedback, rapid defect detection, and a more maintainable and reliable test suite.

- **Shift-Left Testing**: We will integrate testing activities into the earliest stages of the development lifecycle.
- **Automation**: We will automate tests at all levels where feasible to ensure efficiency and repeatability.
- **Continuous Testing**: All automated tests will be integrated into the CI/CD pipeline to provide continuous feedback on the quality of the codebase.

## 3. Test Levels

The following test levels will be employed:

- **Unit Testing**: To verify that individual components (functions, classes) work as expected in isolation.
- **Contract Testing**: To ensure that the API adheres to its defined specification.
- **Integration Testing**: To validate the interactions between different components of the application.
- **End-to-End (E2E) Testing**: To test the complete application flow from the user's perspective.
- **Security Testing**: To identify and mitigate potential security vulnerabilities.

## 4. Test Scope per Phase

### Phase 1: Foundation & Design

This phase focuses on planning and setup. While no code will be written, the following quality-related activities will be performed:

- **Static Analysis Setup**:
    - **Objective**: Ensure that linting and static analysis tools are correctly configured for Python and TypeScript.
    - **Tools**: `isort`, `black`, `flake8`, `pylint`, `eslint`.
    - **Verification**:
        - Create sample "bad" code files that violate defined rules.
        - Run the linters to confirm that they correctly identify and report all violations.
- **Test Strategy Definition**:
    - **Objective**: Finalize and document the test strategy, test levels, and entry/exit criteria.
    - **Deliverable**: This `testplan.md` document.

### Phase 2: Backend Development

This phase focuses on building the FastAPI backend.

- **Unit Tests (`pytest`)**:
    - **Scope**: Test individual functions and classes in `app/services/` and `app/api/`.
    - **Scenarios**:
        - **Service Layer**:
            - Test that the `football_api.py` service correctly calls the external API.
            - Mock the external API to test different response scenarios (e.g., success, failure, empty data).
            - Verify that the in-memory caching logic works as expected.
        - **API Logic**:
            - Test data transformation and validation logic within the API endpoints.

- **Contract Tests (`schemathesis`)**:
    - **Scope**: Validate the OpenAPI schema generated by FastAPI.
    - **Scenarios**:
        - Automatically test all endpoints (`/api/v1/clubs`, `/api/v1/nations`, `/api/v1/leagues`) for compliance with the OpenAPI specification.
        - Ensure that the API correctly handles invalid data types, missing fields, and other edge cases.

- **Integration Tests (`behave`)**:
    - **Scope**: Test the interaction between the FastAPI application and its components.
    - **Scenarios**:
        - **BDD - Successful Data Retrieval**:
            - `GIVEN` the application is running
            - `WHEN` a `GET` request is made to `/api/v1/clubs`
            - `THEN` the response status code should be `200`
            - `AND` the response body should be a valid JSON array of clubs.
        - Repeat for `/api/v1/nations` and `/api/v1/leagues`.
        - **BDD - External API Failure**:
            - `GIVEN` the external football API is unavailable
            - `WHEN` a `GET` request is made to `/api/v1/clubs`
            - `THEN` the API should return an appropriate error response (e.g., `503 Service Unavailable`).

### Phase 3: Frontend Implementation

This phase focuses on building the React frontend.

- **Unit/Component Tests (`React Testing Library`)**:
    - **Scope**: Test individual React components in isolation.
    - **Scenarios**:
        - **`CardForm.tsx`**:
            - Test that input fields correctly update the component's state.
            - Verify that the "Randomize" button populates the stats fields.
        - **`CardPreview.tsx`**:
            - Test that the component correctly renders the card data passed to it.
        - **`CardCreator.tsx`**:
            - Test that the "Rating" stat is correctly calculated and updated when `DEF`, `CTRL`, or `ATT` values change.
        - **`storage.ts`**:
            - Mock `localStorage` to test `saveCard()`, `getSavedCards()`, `updateCard()`, and `deleteCard()` functions.

- **End-to-End Tests (`Playwright`)**:
    - **Scope**: Test critical user journeys from the browser.
    - **Scenarios**:
        1.  **Full Card Creation and Save**:
            - A user navigates to the app.
            - Fills in the player name.
            - Selects club, nationality, and league from dropdowns.
            - Clicks "Randomize" to get stats.
            - Uploads a local image file.
            - Selects a card background.
            - Clicks "Save".
            - The test will verify that the card is present in the "My Cards" gallery.
        2.  **Load and Edit Saved Card**:
            - A user navigates to the "My Cards" gallery.
            - Clicks on a saved card.
            - The card loads into the editor.
            - The user changes the player's name.
            - Clicks "Save".
            - The test will verify that the card in the gallery is updated.
        3.  **Print Card**:
            - A user creates a new card.
            - Clicks the "Print" button.
            - The test will verify that the browser's print dialog is invoked.
        4.  **Input Validation**:
            - Test that providing a non-image URL in the photo URL field displays an error.
            - Test that non-numeric inputs in the stats fields are handled gracefully.

## 5. Test Deliverables

- **Test Plan**: This document.
- **Test Cases**: Detailed test scenarios will be documented in the source code alongside the automated tests.
- **Test Reports**: Test execution results will be generated by the CI/CD pipeline.
- **Defect Reports**: Bugs will be tracked as issues in the project's version control system.

## 6. Entry and Exit Criteria

### Entry Criteria

- **Phase 1**:
    - Project requirements and architectural plan are documented and approved.
- **Phase 2**:
    - Phase 1 exit criteria are met.
    - Backend development plan and API contract are finalized.
- **Phase 3**:
    - Phase 2 exit criteria are met.
    - Frontend implementation plan is finalized.

### Exit Criteria

- **Phase 1**:
    - All linting and static analysis tools are configured and verified.
    - The test plan is approved.
- **Phase 2**:
    - All planned backend unit, contract, and integration tests are written and passing.
    - The backend API is deployed to a development environment.
    - No critical or major defects are outstanding.
- **Phase 3**:
    - All planned frontend unit/component and E2E tests are written and passing.
    - The complete application is deployed and functional.
    - No critical or major defects are outstanding.
